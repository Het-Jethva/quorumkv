# Retain Client Session state for the life of the Cluster

QuorumKV v1 never reclaims the replicated deduplication state described in ADR-0003. Closing a Client Session marks its record permanently closed and frees an active-session slot, but the record itself is retained: it is what lets a retry of the latest sequence return its cached result instead of taking a second effect, and forgetting it would silently convert an at-most-once guarantee into an at-least-once one. The `active_session_limit` therefore bounds only concurrently open sessions, not the total a Cluster accumulates, so replicated state and every Snapshot written from it grow without bound over a long-lived Cluster. This is a real limitation and not a claim that the growth is acceptable at any scale; it is the deliberate v1 position that a wrong dedup answer is worse than an unbounded one.

The reclamation designs all cost more than v1 is willing to spend. A lease with a time-to-live is the standard answer, but it introduces clock assumptions into a state machine whose determinism ADR-0004 exists to protect: expiry has to be driven by a replicated entry rather than by any Node's local clock, which means a new entry type, a Leader responsible for proposing expirations, a renewal path on the client, and a Snapshot format that survives all of it. A hard cap on total retained sessions is far cheaper but converts unbounded growth into a Cluster that permanently refuses new sessions, which is a worse failure for the fixed three-Node deployment v1 targets. Bounding by count and evicting the oldest records is cheapest of all and is the one option that is actually unsafe, because the evicted record is exactly the one a slow retry needs.

A v2 that wants long-lived Clusters should add lease-based sessions with replicated expiry entries, keep the renewal in the Client rather than the caller, and treat an expired session as permanently closed so the existing typed error already covers it. Until then, operators should treat a QuorumKV Cluster as having a bounded lifetime in total sessions opened, and the demo and benchmark workloads should keep reusing sessions rather than opening one per operation.
